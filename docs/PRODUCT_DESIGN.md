# PaperLens 产品设计方案

> 暂定名：PaperLens<br>
> 文档版本：v0.2<br>
> 日期：2026-09-04<br>
> 状态：macOS 方向已确认，MVP 纵向切片开发中

## 1. 一页结论

PaperLens 的定位不是“再做一个带聊天框的 PDF 阅读器”，而是做一个 **PDF 优先、双语友好、证据可追溯的科研阅读工作台**：

> 找到论文 → 判断是否值得读 → 合法获取全文 → 边读边翻译和理解 → 顺着引用继续发现 → 把结果沉淀为可复用笔记。

首版确定为 macOS 桌面应用，采用本地优先的数据策略。普通 PDF 阅读、批注、书库和本地搜索无需登录；联网论文检索、开放获取解析、翻译、AI 解释、推荐和同步按需启用。Windows、Web 与移动端不进入首版范围。

产品最重要的三个差异点：

1. **理解发生在原文旁边**：翻译、公式、概念和引用都不迫使用户离开当前阅读位置。
2. **每个结论都能回到证据**：AI 内容绑定页码、段落、公式区域或元数据来源，并区分原文、推导和通用知识。
3. **发现到阅读是一条链路**：跨源搜索、引用网络、合法全文入口、阅读器和个人资料库互相打通。

需要诚实限定的承诺：

- “浏览任意期刊”可以在元数据层尽量广覆盖，但卷期完整性取决于数据源。
- “便捷下载主流网站论文”只包括开放获取、官方 API、机构/个人订阅跳转及用户主动导入；产品不绕过付费墙、验证码、访问控制或 DRM。
- 数学解析是辅助理解，不承诺替代教材、同行评审或严格证明。

## 2. 产品目标与非目标

### 2.1 目标

- 把“搜索—获取—阅读—理解—追踪—沉淀”的切换成本降到最低。
- 让英文能力不是阅读专业论文的主要障碍，同时保持中英文句段可对齐。
- 让引用、公式和陌生概念变成可点击、可解释、可继续追溯的对象。
- 建立透明、可控制、不过度成瘾的每日科研推荐。
- 保证 PDF、批注、笔记和引用数据可导出，不把用户锁在产品中。

### 2.2 首版非目标

- 不完整替代 Zotero、EndNote 等成熟参考文献管理器。
- 不生成可直接发表的自动文献综述。
- 不做付费内容聚合站或论文共享站。
- 不首发 EPUB、MOBI、漫画和娱乐阅读能力。
- 不首发实时多人协作、机构知识库或复杂图数据库。
- 不自建全球论文索引，也不把每份 PDF 默认上传云端。

## 3. 目标用户与核心任务

### 3.1 核心用户

| 用户 | 主要困难 | 最需要的价值 |
| --- | --- | --- |
| 本科高年级、硕博研究生 | 英文精读慢、引用链散、公式门槛高 | 快速找到并真正读懂关键论文 |
| 高校教师与科研人员 | 新论文过多、跨来源跟踪困难 | 可信筛选、引用追踪与领域更新 |
| 工程师、量化及独立研究者 | 跨学科术语多、缺少学术数据库习惯 | 直观解释、可获取全文和实践关联 |
| 专业知识工作者 | 时间碎片化、专业文献更新快 | 用较短时间判断论文是否值得深读 |

### 3.2 用户要完成的任务（JTBD）

- 当我开始研究一个问题时，希望快速找到真正相关、并且能明确判断全文获取状态的论文。
- 当我读英文论文时，希望不中断阅读就看到可靠中文翻译。
- 当我遇到公式时，希望先知道直觉和用途，再按需查看符号、前置知识和推导。
- 当我遇到陌生概念时，希望知道它在本文中的具体含义，而不只是百科定义。
- 当我点击引用时，希望立即知道被引论文讲什么、作者为何引用、是否可读。
- 当我没有明确检索目标时，希望每天获得少量、理由清晰且可以调节的推荐。
- 当我长期关注主题、作者、期刊或会议时，希望方便浏览最新内容并订阅更新。

## 4. 产品原则

1. **阅读优先**：PDF 永远是主画布，辅助能力默认收起或贴边出现。
2. **渐进呈现**：先给一句直觉，再让用户展开细节、推导和来源。
3. **证据优先**：翻译、总结和解析必须保存原文锚点。
4. **明确不确定性**：界面区分“原文明示”“根据原文推导”“通用背景知识”“无法确认”。
5. **合法获取**：来源、版本、许可和访问方式始终可见。
6. **本地优先**：不登录也能读本地文件，上传全文必须由用户主动选择。
7. **可迁移**：支持原始 PDF、带批注 PDF、Markdown、BibTeX、RIS、CSL-JSON 等导出路径。
8. **少而精**：推荐以每日 5–10 篇为主，不做无尽信息流。

## 5. 市场参照与机会

这不是完整竞品评估，只用于确定首版边界：

| 产品/类型 | 已验证的强项 | PaperLens 的机会 |
| --- | --- | --- |
| Zotero | 资料库、引用管理、PDF 批注与笔记；其批注存数据库并可导出到 PDF，利于同步和避免文件冲突 | 不重做全部引用管理，重点补足双语、公式、上下文解释和发现链路 |
| Semantic Reader | 在原文旁展示引用卡、定义和智能略读，证明“增强型论文阅读”有明确价值 | 做到任意用户导入 PDF、本地优先、中文体验和更完整的获取路径 |
| Readwise Reader | 跨格式、跨平台、同步、导出与音频阅读体验成熟 | 聚焦学术元数据、引用图谱、期刊跟踪和数学理解 |
| 普通 PDF + 通用聊天机器人 | 使用门槛低 | 解决页码定位、引用识别、术语一致性、数学验证和来源可信度问题 |

公开依据可参见 [Zotero PDF Reader 文档](https://www.zotero.org/support/pdf_reader)、[Zotero 批注存储说明](https://www.zotero.org/support/kb/annotations_in_database)、[Semantic Reader 官方介绍](https://www.semanticscholar.org/product/semantic-reader) 和 [Readwise Reader 官方介绍](https://readwise.io/read/)。

## 6. 信息架构

一级导航控制在五项：

- **首页**：继续阅读、今日推荐、关注更新、待处理导入。
- **发现**：统一搜索、期刊/会议浏览、引用网络、保存的检索。
- **资料库**：论文、电子书、收藏夹、标签、阅读状态、重复项。
- **笔记**：批注、论文笔记、知识卡片、跨论文主题页和导出。
- **设置**：账户、AI 与翻译、数据源、机构访问、同步、隐私和存储。

阅读器以沉浸页面或标签页打开，不长期占用一级导航。

~~~text
首页 ── 今日推荐 / 继续阅读 / 关注更新
发现 ── 搜索 / 论文详情 / 引用图谱 / 期刊与会议
资料库 ── 收藏夹 / 标签 / 状态 / 文件版本
笔记 ── 批注 / 知识卡 / 主题笔记 / 导出
阅读器 ── PDF / 翻译 / 解释 / 引用 / 笔记
~~~

## 7. 核心页面设计

### 7.1 首页

首屏只突出三件事：

1. 继续阅读：显示最近阅读位置、进度和上次笔记。
2. 今日推荐：默认 5–10 篇，显示一句话贡献和推荐原因。
3. 关注更新：主题、作者、期刊、会议和保存检索的新内容。

推荐卡片至少包含：中英文标题、作者、年份、渠道、一句话贡献、推荐原因、全文状态，以及“保存”“略过”“不感兴趣”“打开”操作。

### 7.2 发现与搜索

搜索框接受关键词、自然语言、标题、DOI、PMID、arXiv ID、作者、期刊或粘贴的网址。高级筛选包括：

- 年份、领域、作者、机构、期刊/会议；
- 论文类型、开放获取状态、是否有 PDF；
- 相关度、日期、领域内归一化影响力；
- 综述、数据集、方法论文、复现或争议论文。

搜索结果先跨源去重，再以统一卡片呈现。每条结果都展示：

- 元数据来源与更新时间；
- “开放获取”“机构访问”“订阅跳转”“仅摘要”“暂无全文”状态；
- 预印本、作者接受稿、正式出版版等版本标签；
- 保存、预览、直接下载或去来源网站的明确操作。

自然语言搜索首版可先把用户问题转换成关键词、主题和筛选条件，结果仍由学术索引返回；不要用语言模型凭空生成论文条目。

### 7.3 论文详情页

页面由四块组成：

- **身份**：标题、作者、机构、期刊、日期、DOI/其他 ID、版本。
- **快速判断**：摘要、中文摘要、研究问题、方法、数据、结论、局限。
- **关系**：参考文献、被引论文、相似论文、关键前置和后续工作。
- **获取**：所有可用位置、许可、文件版本、机构链接与导入按钮。

AI 生成的结构化解读必须附原文位置；只有摘要时，要醒目标明“仅依据摘要”。

### 7.4 PDF 阅读器

建议采用可折叠三栏布局：

~~~text
┌────────────┬─────────────────────────────────┬──────────────────────┐
│ 目录/缩略图 │                                 │ 翻译 / 解释 / 引用    │
│ 搜索/批注   │            PDF 原文             │ 问答 / 笔记 / 证据    │
│ 可折叠      │                                 │ 可折叠                │
└────────────┴─────────────────────────────────┴──────────────────────┘
                     选中文本后出现紧凑操作条
          翻译 · 解释 · 公式 · 提问 · 高亮 · 笔记 · 引用
~~~

阅读器基础能力：

- 标签页、多级目录、缩略图、页面跳转、全文搜索、缩放、旋转和双页模式；
- 高亮、下划线、区域、文本、手写和批注；
- 记住每篇文献的页码、缩放、侧栏和翻译状态；
- 点击笔记跳回原文；导出原始 PDF 或生成带批注副本；
- 对扫描件、加密文件、损坏文本层和 OCR 低置信度给出清楚提示。

### 7.5 引用关系页

默认不直接展示复杂“蜘蛛网”，先给可操作的分组列表：

- 本文引用的关键前置工作；
- 引用本文的后续工作；
- 方法、数据集或任务相同的论文；
- 综述/教程；
- 观点相反、复现失败或指出局限的论文。

用户主动进入“图谱模式”后，再按年份、作者、主题和引用方向筛选，支持查看两篇论文之间的最短引用路径。

## 8. 英中翻译体验

提供三种互补模式：

1. **划词/短句翻译**：浮层即时显示，不打开侧栏。
2. **段落对照**：默认推荐；右栏展示与当前段落对齐的中文。
3. **整页双栏**：用于连续精读，但不把译文覆盖在 PDF 上。

质量要求：

- 公式、变量、引用编号、DOI、图表编号和代码保持不变；
- 点击译文定位原句，点击原句定位译文；
- 术语第一次出现时显示“中文译名（英文原词）”；
- 允许锁定术语译法，并按学科维护个人术语表；
- OCR 不清或句子跨栏顺序存疑时显示警告；
- 翻译缓存包含原文哈希、目标语言、术语表版本和模型版本；
- 用户可一键反馈“误译”“术语不一致”“漏译公式”。

首版不做整篇中文重排 PDF。该方案成本高、容易破坏版式，也让译文难以回到原文证据。

## 9. 公式与概念解析

### 9.1 公式卡片

用户框选公式后，右栏按以下层次展示：

1. 一句话直觉：这个公式解决什么问题。
2. 本文作用：作者为什么在这里使用它。
3. 符号表：变量含义、维度、单位和取值范围。
4. 前置知识：理解它需要哪些概念。
5. 逐步推导：默认折叠，注明每一步所用假设。
6. 最小数值例子：代入简单数据验证结果。
7. 几何/概率图示：适用时再显示。
8. 原文依据：上下段落、前文定义、附录和被引来源。

识别出的 LaTeX 和符号允许用户修正。可计算的代数、微积分或数值例子可以交给符号计算工具复核，但界面不能把它包装成通用定理证明。

### 9.2 概念卡片

概念解释区分：

- 通用定义；
- 本文语境中的具体定义；
- 与近似概念的区别；
- 一个直观例子；
- 本文首次定义和后续使用位置；
- 推荐前置阅读。

默认只显示两三句话，用户再选择“展开严格定义”或“举个例子”。

## 10. 引用卡与相关推荐

点击正文的引用编号或作者年份引用时，原地弹出引用卡：

- 被引论文标题、作者、摘要/一句话贡献；
- 当前句为何引用它：支持、对比、采用方法、使用数据或指出局限；
- 当前引用上下文与来源页码；
- 全文状态和可用版本；
- 保存、预览、打开、加入稍后阅读。

“为何引用”只能依据当前上下文分类；没有全文或解析失败时只展示元数据，不虚构引用意图。

相关推荐至少分为：相似研究、关键前置、后续改进、同方法/数据集、综述教程、相反或争议观点。每个推荐显示确定性理由，例如“你关注了该作者”“与已读论文共享 8 篇参考文献”，而不是让语言模型临时编造理由。

## 11. 每日推荐与期刊浏览

### 11.1 冷启动

首次使用让用户选择领域、关键词、作者/期刊、偏好的论文类型，以及 3–5 篇种子论文。也可通过导入 BibTeX/RIS 或现有资料库建立兴趣模型。

### 11.2 候选与排序

推荐系统首版采用可解释混合方案：

1. 候选生成：关注项更新、保存检索、已读论文引用邻域、语义相似论文和编辑探索池。
2. 排序：语义相关度、时间、领域内归一化影响力、作者/期刊偏好、开放获取状态和用户反馈。
3. 多样性重排：限制同作者、同渠道或同一窄主题连续出现。
4. 用户反馈：保存、读完、略过、不感兴趣和“少推荐此主题”。

每天可以固定包含“高度相关”“关注更新”“经典补课”“相邻领域”四类，避免只追热点或形成信息茧房。

### 11.3 期刊/会议浏览

支持按学科、期刊、会议、卷期、最新发表、高被引、热门增长、开放获取和综述浏览。期刊实体以 ISSN 为主标识，会议按规范名称与系列标识去重。

由于不同来源的卷期数据并不总是完整，页面必须显示来源和最后更新时间，不能用“全部收录”误导用户。

## 12. 全文获取与渠道策略

### 12.1 获取状态模型

每个可用位置都记录：来源、URL、访问方式、论文版本、许可、发现时间、最后验证时间和可信度。

~~~mermaid
flowchart TD
    A[找到论文或粘贴 DOI/URL] --> B{有已验证的开放获取位置?}
    B -- 是 --> C[显示版本与许可并由用户一键下载]
    B -- 否 --> D{用户有机构或个人订阅?}
    D -- 是 --> E[系统浏览器完成登录与下载]
    E --> F[用户确认后自动导入]
    D -- 否 --> G[打开出版社页面/馆际互借/联系作者]
    G --> H[暂存元数据和摘要，不缓存未授权全文]
~~~

### 12.2 数据源分工

截至本方案日期，没有单一来源能同时可靠覆盖检索、引用、推荐和全文。建议采用“开放学术图谱 + DOI 权威元数据 + 合法全文解析器 + 学科专库”的组合。

| 来源 | 主要用途 | 接入优先级 | 关键边界 |
| --- | --- | --- | --- |
| [OpenAlex](https://help.openalex.org/api/) | 主检索、作者/机构/来源、主题、引用、相关作品和 OA 位置 | P0 | 作为发现骨架；元数据开放不代表其链接 PDF 可自由转载，按全文许可判断 |
| [Crossref REST API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/) | DOI 校验、出版元数据、许可、勘误/撤稿、部分参考文献和引文导出 | P0 | 全文链接只是来源；参考文献取决于出版商提交，摘要也可能受版权保护 |
| [Unpaywall](https://unpaywall.org/data-format) | 按 DOI 解析 OA 位置、版本、许可和 PDF 候选 | P0 | 解决“哪里有合法开放副本”，不额外授予内容版权；许可未知不能推定可再分发 |
| [Semantic Scholar API](https://www.semanticscholar.org/product/api) | 引用、参考文献、语义搜索和推荐候选 | P1/授权闸门 | [当前 API 协议](https://api.semanticscholar.org/license/)对商业嵌入有限制；商业化前需取得适用许可，不能成为无替代核心依赖 |
| [arXiv API](https://info.arxiv.org/help/api/index.html) | 数理、计算机等预印本检索、新论文订阅 | P1 | 遵守速率、品牌、致谢和 [API 条款](https://info.arxiv.org/help/api/tou.html)；优先让用户从 arXiv 页面发起下载，不默认服务器镜像 |
| [PubMed / PMC](https://pmc.ncbi.nlm.nih.gov/tools/developers/) | 生物医学检索、相似记录、ID 转换和开放子集 | P1（医学首发则 P0） | PubMed 不是全文库；PMC 并非所有文章都可自动复用，按文章许可及指定 API 获取 |
| [DOAJ](https://doaj.org/) | 开放获取期刊和文章目录、期刊浏览 | P1 | 期刊总体 OA 不等于忽略具体文章许可；卷期时效按接口类型不同 |
| [CORE API](https://core.ac.uk/services/api) | 机构仓储、无 DOI 文献和 OA 全文补充 | P2/商务闸门 | 产品化与商业使用需按当期条款确认；底层论文权利仍归原权利人 |
| [万方开放平台](https://apps.wanfangdata.com.cn/open/docs) | 中文文献元数据及未来正式合作 | P2 | 只有获得 API 和内容授权后才做深度接入 |
| CNKI、维普及商业出版商 | 官方落地页、机构访问和未来合作 | P1/P2 | 不抓登录页、不共享账号、不绕过验证码或下载限制 |
| [Google Scholar](https://scholar.google.com/intl/us/scholar/help.html) | 外部搜索入口和用户手动跳转 | 仅跳转 | 官方不提供批量访问并要求自动软件尊重 robots.txt，不作为后端抓取源 |

建议落地顺序：

1. 首版：OpenAlex 主检索/引用图谱 + Crossref DOI 校验/引文导出 + Unpaywall OA 解析。
2. 学科扩展：arXiv、PubMed/PMC、DOAJ。
3. 推荐增强：先用 OpenAlex 相关作品、主题/作者/期刊关注和用户行为；获得许可后再接 Semantic Scholar。
4. 仓储补全：取得适用许可后再接 CORE 和中文商业数据库。

### 12.3 下载体验

- OA：应用内一键下载，先显示“版本 + 来源 + 许可”。
- 机构订阅：使用系统浏览器或学校代理完成认证；应用不保存机构密码。
- 商业来源：打开官方页面，用户自行合法下载后通过分享菜单、拖放或浏览器扩展导入。
- 无全文：保留元数据，提供馆际互借、联系作者、查找预印本或设置提醒的入口。
- 每个文件用 SHA-256 去重，保留原始文件名、来源 URL 和导入时间。

浏览器扩展只负责“保存当前元数据/用户已获得的 PDF 到 PaperLens”，不模拟批量点击、不破解验证码，也不把登录 Cookie 上传到服务端。

## 13. 资料库、笔记与可迁移性

### 13.1 资料库

- 状态：收件箱、稍后阅读、阅读中、已读、归档。
- 组织：收藏夹、标签、智能筛选、保存搜索。
- 去重：DOI → PMID/PMCID/arXiv ID → 标题、年份和第一作者模糊匹配。
- 一篇论文可以有多个文件版本，不能把“论文”和“某个 PDF 文件”混为一条记录。

### 13.2 笔记

- 每条批注自动保存原文、页码、坐标、颜色和论文引用。
- 可把多个批注拖入论文笔记或主题笔记。
- AI 生成内容和用户书写内容视觉上明确区分。
- 知识卡片保存概念、简释、严格定义、例子和来源。

### 13.3 导入导出

- 导入：PDF、文件夹、DOI/URL、BibTeX、RIS、CSL-JSON；后续支持 Zotero。
- 导出：原始 PDF、带批注 PDF、Markdown、BibTeX、RIS、CSL-JSON、批注 JSON。
- 删除账户时能下载数据包并明确删除云端副本；本地文件不受账户状态影响。

## 14. MVP 功能范围

### 14.1 P0：必须完成

- 本地导入、拖放和文件去重；
- PDF 阅读、目录、全文搜索、阅读进度；
- 高亮、批注、标签和 Markdown 导出；
- DOI/标题识别、统一元数据与版本模型；
- OpenAlex/Crossref 搜索聚合与去重；
- 通过 Unpaywall/OpenAlex 返回的合法 OA 位置下载，并支持 DOI/出版社页面跳转；
- 划词和段落级英中翻译；
- 选中文字的本文语境解释；
- 选中公式的基础解析、符号表和原文依据；
- 参考文献识别、引用卡和基础相关论文；
- 简版每日推荐；
- 关注主题、作者、期刊并浏览基础更新；
- 无需注册的本地模式，以及云同步接口预留。

### 14.2 P1：Beta

- 扫描件按页 OCR、版面重建和质量提示；
- 引用图谱、高级推荐分类和反馈闭环；
- 批注与设置同步，PDF 文件同步由用户单独开启；
- 浏览器扩展和机构 OpenURL 解析器；

### 14.3 P2：正式版之后

- EPUB 与普通电子书体验；
- Web 与移动端；
- 团队共享资料库、机构 SSO；
- 更多中文数据库和出版商正式合作；
- 可交互数学图示、跨论文知识图谱和综述辅助。

## 15. MVP 验收场景

1. 用户输入自然语言主题，能得到去重后的真实论文，并看见元数据来源和全文状态。
2. 对有合法 OA 版本的论文，用户最多两次操作即可下载并打开；没有 OA 时不会出现误导性的“免费下载”。
3. 用户拖入本地 PDF 后，无需注册即可阅读、搜索、批注、关闭并恢复上次位置。
4. 用户选中英文段落后能看到对齐中文，公式、编号和引用标记不被改写，并可跳回原句。
5. 用户选中公式后能看到直觉、符号、本文用途、推导入口和证据位置；低置信度识别会提示修正。
6. 用户点击可识别引用后能看到被引论文元数据、当前引用上下文、获取状态和保存操作。
7. 用户完成兴趣设置或导入种子论文后，次日能获得有限数量、理由透明且可反馈的推荐。
8. 网络断开时，已下载 PDF、批注、笔记和本地搜索仍可工作；联网能力明确降级。

## 16. 推荐技术架构

### 16.1 总体结构

~~~mermaid
flowchart LR
    subgraph Desktop[macOS 桌面端：本地优先]
        UI[React + TypeScript]
        PDF[PDF.js 阅读与文本层]
        Core[Tauri/Rust 权限与文件核心]
        Local[(SQLite + FTS5)]
        Files[(本地 PDF/Sidecar)]
        UI --> PDF
        UI <--> Core
        Core <--> Local
        Core <--> Files
    end

    subgraph Cloud[云端增强：按需]
        API[FastAPI 模块化单体]
        Worker[解析/OCR/AI Worker]
        PG[(PostgreSQL + pgvector)]
        Cache[(Redis)]
        Obj[(可选对象存储)]
        API <--> Worker
        API <--> PG
        API <--> Cache
        Worker <--> Obj
    end

    subgraph Sources[外部学术来源]
        Meta[OpenAlex/Crossref]
        OA[Unpaywall/arXiv/PMC]
        Pub[出版社/机构链接]
    end

    Desktop <-- HTTPS/SSE --> API
    API <--> Sources
~~~

### 16.2 客户端

- **推荐**：Tauri 2 + React + TypeScript；Tauri 使用系统 WebView 和 Rust 核心，适合权限清晰的桌面应用，参见 [Tauri 架构](https://v2.tauri.app/concept/architecture/)。
- **PDF**：PDF.js，封装在 DocumentRenderer 接口后；它提供解析、显示层和可扩展查看器，采用 Apache 2.0，参见 [PDF.js Getting Started](https://mozilla.github.io/pdf.js/getting_started/)。
- **本地数据**：SQLite + FTS5 保存资料库、批注、笔记、翻译缓存、全文索引和同步队列。
- **文件存储**：原 PDF 只读保存，批注默认放 sidecar/数据库；带批注 PDF 通过导出任务生成。
- **技术闸门**：先用 50–100 份复杂 PDF 验证 Tauri/WKWebView/PDF.js。若文本选择、内存或渲染不达标，再评估 Electron 或 PDFium；不为首版额外承担跨平台兼容成本。

### 16.3 云端

- FastAPI 模块化单体：账户同步、学术搜索聚合、访问解析、AI 编排、推荐和管理接口。
- PostgreSQL + pgvector：用户数据、元数据缓存、引用边和混合检索。
- Redis：队列、短期缓存和来源限流；后台任务状态仍落 PostgreSQL。
- Worker：科学 PDF 结构化、OCR、公式识别、向量化和推荐批任务。
- 对象存储只保存用户明确开启同步的文件；普通 AI 请求不因此永久保存全文。

早期不拆微服务、不上 Kubernetes、Neo4j 或独立向量数据库。模块化单体加独立 Worker 足以支撑验证和早期用户。

### 16.4 数据源适配层

每个 Provider 实现统一能力：

~~~text
search
resolveIdentifiers
getWork
getReferences
getCitations
listVenueWorks
getDownloadCandidates
~~~

适配器必须内置速率限制、退避、缓存、熔断、契约测试和来源字段映射。任何聚合字段都保存 provenance，不能静默覆盖不同来源的冲突值。

## 17. 文档处理与锚点设计

### 17.1 核心数据模型

| 实体 | 含义 |
| --- | --- |
| Work | 抽象学术作品及 DOI、作者、期刊和引用关系 |
| WorkVersion | 预印本、作者接受稿、正式出版版等版本 |
| SourceLocation | 元数据或全文位置、访问方式与许可 |
| FileAsset | 用户实际拥有的某个 PDF，含哈希和解析状态 |
| Annotation | 高亮、区域、文字或手写批注及复合锚点 |
| TranslationBlock | 对齐原文的翻译、术语表和模型版本 |
| Explanation | 公式/概念/问答、证据锚点、推断类型和置信度 |
| ReadingEvent | 阅读进度及明确授权用于推荐的交互信号 |
| Follow / FeedItem | 关注对象、推荐候选、理由和反馈 |

### 17.2 PDF 锚点

批注不能只存页码。建议保存：

~~~text
document_hash
page_index / page_label
PDF CropBox 坐标中的 quad 列表
归一化坐标
exact_text + prefix + suffix
span_ids
rotation / extractor_version
~~~

屏幕坐标和 OCR 像素框都转换到同一 PDF 用户空间。文件版本变化时，利用原文和上下文做模糊重定位，并明确显示置信度。

### 17.3 处理流水线

~~~text
导入 → 文件类型与安全检查 → SHA-256 去重 → 文本质量检测
  ├─ 文本型 PDF：PDF.js 文本层 + 科学文档结构化
  └─ 扫描型 PDF：按需渲染/矫正 → OCR → 阅读顺序重建
→ 章节、段落、公式、图表、参考文献 → 坐标对齐
→ 本地全文索引 → 用户允许时生成向量或调用云端 AI
~~~

科学 PDF 结构化可评估 GROBID；它适合标题、作者、章节、正文、参考文献和引用标记提取，但不能替代扫描件 OCR，参见 [GROBID 官方介绍](https://grobid.readthedocs.io/en/latest/Introduction/)。

## 18. AI 与可信度设计

### 18.1 上下文包

每次翻译或解释只发送完成任务所需内容：选区、相邻段落、当前章节标题、相关公式/定义和必要引用元数据。用户可以看到本次即将发送的范围。

### 18.2 结构化输出

服务端要求模型返回结构化字段：

~~~text
answer
claim_type: source | derived | background | uncertain
source_anchors[]
assumptions[]
symbol_table[]
confidence
model_version
~~~

客户端只把有合法锚点的内容标成“论文中明确写道”。没有证据时应缩小回答或明确拒答。

### 18.3 安全护栏

- PDF 正文属于不可信输入，不能覆盖系统指令、请求工具调用或执行代码。
- 翻译不改变公式、变量、引用和标识符。
- 数学结果尽量用可执行计算做局部复核，并显示无法验证的步骤。
- 不把推荐论文标题、DOI 或引用交给模型凭空生成。
- 对医学、法律、金融等高风险结论显示“研究解释，不构成专业建议”。
- 允许用户查看模型、来源和时间，并反馈错误。

### 18.4 成本控制

- 只对文本质量差的页面 OCR；
- 默认选区/段落翻译，整篇任务异步并预估成本；
- 按内容哈希、术语表和模型版本缓存；
- 小模型处理分类、路由和候选解释，大模型只处理复杂解析；
- 原文直接使用多语种嵌入，不为每种译文重复向量化；
- 每日推荐批量计算，CPU/GPU 任务分队列并可取消。

模型供应商通过统一网关抽象，避免把产品锁死在单一 API；密钥存系统 Keychain/Credential Manager。

## 19. 隐私、安全与版权

### 19.1 三种清晰模式

| 模式 | 本地数据 | 发送到云端 |
| --- | --- | --- |
| 本地模式 | PDF、索引、批注和笔记 | 仅公开元数据搜索请求 |
| AI 增强模式 | 原文件仍默认本地 | 用户触发时发送必要选区和上下文 |
| 文件同步模式 | 本地保留副本 | 用户单独开启后加密上传 PDF |

真正端到端加密的文件不能同时让服务器直接做全文检索和 AI。若提供 E2EE，同步文件应在客户端解密和检索，不宣传含糊的“全程加密 AI”。

### 19.2 安全措施

- PDF 解析、OCR 和公式识别在资源受限的隔离 Worker 中运行；禁止 PDF 内嵌脚本、Launch Action 和自动附件执行。
- Tauri capability 只开放必要目录和命令；自动更新包必须签名。
- 云端下载防 SSRF、内网 IP、DNS 重绑定和恶意重定向，并验证 MIME、PDF 文件头、大小和哈希。
- 日志默认不记录论文正文、选区、文件名、翻译内容和访问令牌。
- 账户采用 OIDC/OAuth PKCE、TLS、租户隔离和短时签名 URL。
- 版权规则以 SourceLocation 为中心执行：许可未知不等于可自由再分发。

## 20. 非功能目标

以下是 MVP 的工程目标，需在技术验证后用基准设备修订：

- 20 MB 本地文本型 PDF 首屏 p95 小于 2 秒；大文档采用页面虚拟化，不一次加载全部页面。
- 资料库 10,000 条时，本地常用搜索 p95 小于 300 ms。
- 选中文本后的操作条在 100 ms 内出现；网络正常时翻译首段目标小于 2.5 秒。
- 支持至少 100 MB、500 页 PDF 的渐进阅读；更大文件能降级而非直接崩溃。
- 批注在缩放、旋转、重启后保持定位；坐标系统有截图回归测试。
- 已下载内容离线可读；同步队列幂等、可恢复并能处理删除 tombstone。
- Beta 目标无崩溃会话率不低于 99.5%。
- 键盘导航、可调字号、对比度和屏幕阅读器语义纳入首版验收。

## 21. 测试策略

建立 50–100 份“金标准 PDF”集合，覆盖双栏/三栏、中英文、连字符、复杂字体、公式、表格、扫描、歪斜、低清、旋转、CropBox、加密、损坏、超长和超大文档。

关键测试包括：

- PDF 坐标正反变换、批注位置和截图回归；
- OCR 字符错误率、阅读顺序、版面框和低置信度提示；
- DOI、参考文献和引用标记解析准确率；
- 翻译术语一致性及公式/编号零破坏；
- AI 证据覆盖率、引用定位率和无依据回答率；
- 推荐相关性、覆盖率、多样性、重复率与负反馈；
- 离线、同步冲突、幂等重试和删除；
- 外部 API 限流、超时、缓存和字段变化的契约测试；
- PDF fuzz、安全扫描、依赖锁定和 SBOM。

GitHub Actions 后续覆盖 TypeScript、Rust、Python 测试，以及 Apple Silicon/Intel macOS 构建。正式发行需要 Developer ID 签名、macOS notarization 和签名自动更新。

## 22. 指标体系

北极星指标：**每周有效阅读会话数**。

“有效阅读会话”建议定义为：达到最低阅读时长，并完成批注、笔记、引用追踪、公式/概念理解或标记读完中的至少一项。

产品指标：

- 搜索到打开论文的成功率和耗时；
- 合法全文获取成功率；
- 首次导入到开始阅读的耗时；
- 翻译、公式和概念解释的有用率；
- AI 结论带可用原文锚点的比例；
- 推荐的打开率、保存率、读完率和负反馈率；
- 关注主题/期刊后的 7 日与 30 日留存。

护栏指标：

- 错误 DOI/元数据合并率；
- 无来源 AI 结论率和数学错误反馈率；
- 误标“免费下载”次数；
- 下载失败、推荐重复、崩溃和隐私/版权事件数。

## 23. 商业模式建议

软件收费不能与论文访问权混淆。可以考虑：

- **免费版**：本地阅读、批注、资料库、公共元数据搜索和有限 AI 额度。
- **个人专业版**：更多 AI、跨设备同步、高级推荐、全文处理和浏览器扩展。
- **团队/机构版**：SSO、共享资料库、管理员策略和机构数据源合同。

不销售、转售或共享用户无权再分发的付费论文。中文数据库和商业出版商的深度接入单独走商务授权。

## 24. 实施路线与闸门

下面是 3–5 人团队的粗略计划；个人开发通常需要更久，最终以技术验证结果为准。

### 阶段 0：产品与技术验证（2–3 周）

- 完成首页、搜索、阅读器和引用卡的可点击原型；
- 用金标准 PDF 验证 Tauri/PDF.js、文本选择与坐标锚定；
- 打通 Crossref/OpenAlex/Unpaywall 和一条翻译链路；
- 完成数据源条款、版权和隐私清单。

**闸门**：复杂 PDF 基准、合法获取流程和核心阅读交互通过评审。

### 阶段 1：macOS MVP（8–10 周）

- 本地书库、PDF 阅读、搜索、批注与笔记；
- 多源搜索、版本识别和 OA 下载；
- 选区/段落翻译、概念与基础公式解释；
- 简版每日推荐、关注项更新与基础期刊浏览；
- 无需登录的本地模式。

**闸门**：完成“搜索 → 合法获取 → 阅读 → 翻译/解释 → 保存笔记”的端到端闭环。

### 阶段 2：研究阅读 Beta（8–12 周）

- OCR、科学文档结构化、参考文献和引用卡；
- 账户、批注同步、全文问答和更可靠的数学解析；
- 推荐与反馈的离线评估集。

### 阶段 3：发现系统增强（6–8 周）

- 更成熟的每日推荐、完整期刊卷期、作者/主题关注反馈；
- 引用图谱、浏览器扩展、机构链接和更多来源。

### 阶段 4：扩展格式与平台

- Web、移动端、EPUB、团队协作和机构能力按真实用户数据排期。

## 25. 建议仓库结构

设计通过后建议采用 monorepo：

~~~text
apps/
  desktop/          # Tauri + React
  web/              # macOS 产品验证后的可选 Web 客户端
  mobile/           # macOS 产品验证后的可选移动端
packages/
  domain/           # Work、FileAsset、Annotation 等领域模型
  ui/               # 可复用设计系统
  pdf-anchors/      # PDF 坐标与文本锚点
  api-client/       # 生成的类型安全 API 客户端
services/
  api/              # FastAPI 模块化单体
  worker/           # OCR、结构化、AI 与推荐任务
infra/               # 本地开发与部署配置
docs/
  adr/               # 关键架构决策记录
  product/           # 需求、用户流程与验收
~~~

最先实现一条 tracer bullet：

> 输入 DOI/主题 → 返回真实论文 → 解析合法 OA PDF → 在阅读器打开 → 选段翻译 → 点击引用卡 → 保存到本地资料库。

这条纵向链路通过后，再扩大每个模块的深度。

## 26. 评审时需要决定的问题

1. 首发学科是全学科，还是先聚焦计算机/数学/经济等公式密集领域？建议先聚焦 1–2 个领域验证。
2. macOS 最低系统版本，以及 Intel Mac 是否与 Apple Silicon 同期发行？建议先以 Apple Silicon 为主并在发布前决定 Intel 支持范围。
3. 是否允许用户完全不注册使用？本方案建议允许。
4. PDF 是否默认只存本地？本方案建议是，云同步单独开启。
5. 产品走开源、本地买断、订阅，还是混合模式？这会影响 AI 密钥、同步和授权设计。
6. 中文数据库是否已有机构或商务资源？若没有，首版只做官方跳转和用户导入。
7. 是否需要首版兼容 Zotero 工作流？建议至少先做 BibTeX/RIS 导入导出。
8. 产品中文正式名称、视觉气质和目标用户语言尚未确定。

## 27. 结论

最值得优先验证的不是“AI 能回答多少问题”，而是这条核心体验：

> 用户遇到难句、公式、概念或引用时，不离开原文，就能获得简洁、可展开、可验证的帮助，并自然进入下一篇值得读的论文。

只要这条链路明显优于“PDF 阅读器 + 翻译软件 + 搜索引擎 + 聊天机器人”的组合，PaperLens 就有清晰的产品价值。macOS 方向已经确认；接下来以可运行的 tracer bullet 验证搜索、合法全文获取、本地阅读和带原文锚点的理解体验，再逐步扩大渠道与能力。
